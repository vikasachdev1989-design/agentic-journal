2 · How it runs

Data enters by one of two routes. In the app, one drop zone takes any file: each file is offered to every module, the country is read from the file itself, and the original is stored. From the terminal, a guarded write script takes a KEEP backup before it writes anything. A "fail closed" safety setting covers both routes. Published files ship only through deploy.sh after its guards pass, and every read passes the same login gate.

Controls that make the numbers defensible

Month lockA locked month rejects every upload, admins included. To change it you unlock it first, and the unlock is recorded.
Sign-off on lockLocking a month records who signed it off.
Undo pointEach month and CTC period keeps a :prev copy. Restore swaps it back.
CasesEach exception becomes a case with an owner, a due date and a reason code.
Fix onceAn approved correction becomes an id_alias. That NetSuite mis-key never shows up as an exception again.
Audit logEvery write is recorded in audit_log. Database triggers block edits and deletes.
Upload historyEach uploaded original is stored. import_log records its name, sha256, uploader and months touched. A P&L upload is held until that month's salary record is in.
Terminal routeWrites from the terminal go through a guarded script that takes a KEEP backup first. A "fail closed" setting stops writes when a safety check can't run.
BackupsSnapshots of stored originals, plus the masters/ folder for the employee master and charts of accounts.
Access (open issue)The server enforces country access. Page access is only enforced in the browser, so a logged-in user can still fetch a page's data directly.
AI boundaryClaude receives only totals and exception rows, never full payslips. The API key stays on the server.
